# Problem Definition: 始终可见的 Windows 倒数计时提醒

- **Slug**: offline-mode
- **Created**: 2026-09-18T10:00:52+08:00

## Problem Statement

提议者本人在 Windows 上进行有时间限制的活动时，需要在操作任意前台应用的过程中**随时一眼看到倒计时剩余时间**；而现有计时方式下，剩余时间会被正在使用的窗口遮挡、需要主动切换才能查看，导致时间感知中断、容易错过预定结束时刻。该工具为自用，且必须在无后端、不依赖网络服务的前提下完整工作。

> 边界说明：用户对"Windows 内置时钟应用具体哪里不够用"明确选择了**暂不评价**。因此本定义只陈述用户自己的可见性需求，**不断言**内置应用不具备置顶能力（该事实 research 阶段未能在线核实，见开放问题）。

## Affected Users & Stakeholders

- **Users**:
  - **提议者本人（唯一用户）**——日常在 Windows 上做有时间限制的活动，希望剩余时间始终悬浮在所有应用之上、可余光扫视。具体活动类型（专注工作/会议/其他）尚未指定。
- **Stakeholders**:
  - **提议者本人**——同时是使用者、构建者与唯一决策者；无资金方、无团队、无其他利益相关方（[NEEDS CLARIFICATION: 未来是否会分享给他人——本次确认为自用，暂不考虑]）。

## Goals

- **持续可见**：倒计时运行期间，无论前台切换到什么应用，剩余时间指示始终保持可见、不被遮挡。
- **一眼可读**：无需点击或切换窗口即可获得"还剩多久 / 何时结束"的准确信息，扫视成本极低。
- **不再错过结束时刻**：因为结束时间始终在视野内，错过预定节点的情况趋近于零。
- **离线完整可用**：断网、无账号、无任何后端服务的环境下功能完整（"离线"含义经澄清为"纯本地无后端"）。
- **贴合个人工作流**：作为自用工具，行为以提议者自己的使用习惯为准，无需迁就大众需求或上架约束。

## Non-Goals

以下为**拟定的**范围边界（自用单用户前提下的合理收敛，未经用户逐条确认，见开放问题）：

- 不做面向他人的产品：不发布到微软商店、不做分发网站、不考虑货币化。
- 不做任何网络功能：无云同步、无账号、无在线内容、（按当前定义）也无联网遥测。
- 不做跨平台：仅 Windows，不涉及 macOS/Linux/移动端。
- 暂不做多个并行计时器、计时器库/预设管理、番茄钟循环体系、统计与历史报表。
- 不做主题市场、插件化、可扩展脚本等面向"产品化"的能力。

## Success Metrics

自用工具，以用户自陈与自我观察为主，基线均为"当前未测量"：

- **可见性（核心信号）**：在一次主动倒计时中，出现"剩余时间被前台窗口遮挡、需要额外操作才能看到"的次数 = 0。（baseline: unknown——当前依赖手动切回计时窗口，未统计）
- **错过结束时刻次数**：工具投入自用后，因没看到时间而错过预定节点的次数 ≈ 0。（baseline: unknown）
- **使用黏性（定性→定量）**：用户在每次有时间限制的活动中都愿意启动它（定性自陈；若愿意可粗测"有计时需求的场次中实际使用比例"）。（baseline: unknown）
- **离线验证（通过/不通过）**：断开全部网络后，从设定时长到结束提醒的完整流程可正常完成。（baseline: 不存在该工具）
- **扫视耗时（可选，定性）**：获得剩余时间所需的视线移动/操作明显少于现状。（baseline: unknown）

## Cost of Inaction

- 对**用户本人**：继续使用现有计时方式，剩余时间持续被窗口遮挡、需手动切换查看，时间盒活动中的时间感知中断与偶发错过节点会持续发生——影响范围仅限一人，不构成业务或外部损失。
- 对**项目/决策**：该需求的真实强度尚未被现有替代方案的对比验证（用户对内置应用痛点"暂不评价"）；若不构建，最大损失是一个低成本自用工具带来的个人效率改善，风险同样很小。
- research.md 的关键提醒仍然成立：内置时钟与大量免费工具已覆盖基础倒计时，**本项目的全部成立理由系于"始终可见的剩余时间"这一个人需求是否真实且高频**——这是后续 shape/decide 阶段需要验证的核心假设。
