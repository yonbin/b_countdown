# Concept: 始终可见的 Windows 倒计时悬浮指示

- **Slug**: offline-mode
- **Created**: 2026-09-18T10:13:15+0800
- **Recommended option**: A（有前置条件：先花少量时间验证 Option C 不成立）

## Options

### Option A — 极简置顶悬浮计时器（smallest thing that could work）

- **Sketch**: 启动后出现一个小巧、始终置顶的悬浮窗，大号数字显示剩余时间；用最直接的方式设定时长（如输入数字/选分钟），开始、暂停、重置一目了然。外观默认即简洁耐看（实测发现内置应用"太丑"会直接导致弃用，因此最小视觉打磨属于首版范围，但不做主题系统）。到点时数字归零并发出明确的本地提醒（声音/窗口提示）。窗口可拖动到顺手的位置。除此之外什么都没有——没有多计时器、没有统计、没有设置中心。它是一个独立的单一用途小应用，不挂在任何"时钟合集"里。全程本地运行，不联网。
- **Appetite**: **small**（数天，作为预算而非估算；自用、单用户、单一核心交互）
- **Trade-offs**:
  - 赢：最快验证核心假设（"始终可见"是否真的解决问题）；代码面小，平台坑面最小；失败成本极低；完全贴合 problem.md 的核心目标与成功指标（遮挡次数=0）。
  - 牺牲：外观与可调性朴素（透明度、点击穿透、吸附等都不做）；提醒强度、勿扰/全屏下的表现只做到"基本可用"而非"绝不漏接"；无托盘驻留时关掉窗口即退出。
  - 风险：置顶窗口在全屏独占应用（游戏、全屏演示）之上的可见性可能受限；系统睡眠期间的计时需用"绝对结束时刻"处理，否则唤醒后显示错误（research 已标记）。
- **Rabbit holes**:
  - "再调一下样式/位置/透明度"——视觉打磨对单用户自用工具是无底洞，首版应刻意从简。
  - 为追求"绝不漏接"而深入通知权限、勿扰策略、全屏检测——首版只做基本声音+置顶窗口提醒。
  - 输入时长的交互从简单选择膨胀成"预设库/标签/历史"。

### Option B — 增强型悬浮层（robust personal tool）

- **Sketch**: 在 A 的基础上，悬浮指示成为一个"调得很顺手"的常驻层：可调大小/透明度、点击穿透、贴边吸附、托盘驻留与一键唤起；提醒分级（临近结束预警 + 到点强提醒），正确处理睡眠/唤醒与锁屏，勿扰与全屏场景下有兜底行为；重启后可恢复未完成的计时。
- **Appetite**: **medium**（数周）
- **Trade-offs**:
  - 赢：覆盖 problem.md 开放问题中绝大多数行为细节，日常使用可靠性和舒适度显著更高；一次做好睡眠/通知后长期省心。
  - 牺牲：大部分时间花在 Windows 平台边界情况（现代待机、Toast 注册、DPI/多显示器、全屏检测）而非核心价值上；在核心假设尚未被 A 验证之前投入这些，存在"把舒适功能当需求"的风险。
  - 风险：逐周滑向 Option B+（主题、多计时器、统计），即 problem.md 已列为非目标的产品化方向。
- **Rabbit holes**: 点击穿透与可交互性的切换、多显示器/DPI 适配、现代待机（S0）与传统 S3 的差异实测、未打包应用的通知注册、开机自启与单实例管理。

### Option C — 不构建，先验证并使用现有方案（do nothing / verify-then-use）【已于 2026-09-18 部分执行】

- **Sketch**: 不写代码。先用约 10–30 分钟实测两件事：(1) Windows 11 内置时钟应用的计时器在当前系统版本上的紧凑/置顶表现；(2) 成熟免费小工具能否满足"始终可见"。若任一满足，直接采用；若都不满足，再带着确切结论回到 Option A。
- **Appetite**: **small 的零头**（数十分钟实测）
- **执行结果（2026-09-18）**：第 (1) 项已由用户在本机完成 → **内置时钟不满足**：① 不能置顶（核心需求被否）；② 非独立、功能冗余（闹钟/秒表/专注合集）；③ 外观不可接受（"太丑"）。第 (2) 项第三方工具（Hourglass 等）未测试——鉴于内置方案的三条差距均为方向性差距（置顶能力、独立形态、审美），且本项目为自用 small 胃口，剩余竞品验证降级为 specify 期的参考项，不再阻塞。睡眠/唤醒与到点提醒可靠性亦未实测，转入实现期验收点。结论：**Option C 的"停止构建"分支未触发，进入 Option A。**

## Recommendation

**推荐 Option A，但以 Option C 作为强制前置步骤**：先在本机用数十分钟实测内置时钟与一个成熟免费工具的置顶能力。

理由：

1. problem.md 表明项目全部成立理由系于**单一核心假设**——"剩余时间始终可见"对提议者本人真实且高频。Option A 是验证该假设成本最低的形态，且其成功指标直接对应（遮挡次数=0、错过节点≈0、断网完整可用）。
2. 这是**自用工具**（define 阶段已确认），无分发、无多用户、无货币化，Option B 中为他人打磨的可靠性/产品化投入缺乏理由；待 A 用起来证明哪些增强真的高频，再按需升级，比预先做 medium 更诚实。
3. Option C 的前置实测已于 2026-09-18 完成：内置时钟被亲手确认**不能置顶、非独立、外观不可接受**，"重复造内置轮子"的风险被排除，且三条差距直接成为首版验收点（置顶、独立单一形态、简洁耐看的默认外观）。第三方工具未逐一实测，但对自用 small 项目不再构成阻塞。结论：**进入 Option A**。

## Out of Scope (for the recommended option)

继承 problem.md 的全部非目标，并为首版额外收紧：

- 多计时器并行、预设/标签库、番茄循环、历史与统计。
- 透明度/点击穿透/贴边吸附、主题系统与外观深度定制（首版要求"默认即简洁耐看、看得清"，但不提供可配置主题；透明度/穿透/吸附仍属 Option B）。
- 托盘常驻、开机自启、重启后恢复计时。
- 多级提醒、勿扰/全屏/锁屏下的兜底强提醒（首版仅基本本地提醒，全屏独占行为记录为已知限制）。
- 任何网络通信、账号、遥测、自动更新；微软商店与安装包工程（自用可接受最简分发甚至本地构建运行）。
- Windows 10 之外更旧系统、ARM64、非 Windows 平台（最低支持版本本身仍待澄清）。

## Assumptions to Validate

- **[关键，Option C 实测]** 当前 Windows 11 内置时钟计时器不满足提议者的置顶可见需求（背景知识存疑，未在线核实；可能已支持）。
- **[关键]** "始终可见"是高频真实需求而非偶发念头——Option A 自用一两周即可由成功指标验证。
- 一个置顶的普通窗口在提议者的真实前台应用（具体是哪些应用待确认；是否含全屏独占应用）之上能保持可见。
- 以绝对结束时刻而非逐秒递减来计时，足以正确处理睡眠/唤醒场景（S0 现代待机行为需在真机实测）。
- 基本本地提醒（声音 + 置顶窗口）在勿扰开启时对自用场景"足够"，不需要强通知通道。
- 提议者具备或愿意使用所选 Windows 桌面技术栈完成数天量级的实现（技术栈偏好/熟悉度仍待澄清；这是 specify 阶段的输入，不影响概念选择）。
